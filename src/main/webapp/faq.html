Frequently Asked Questions

What is the difference between a feature and a geometry?

There are two distinct kinds of endpoints:

/osm/node/{id}.rdf, /osm/way/{id}.rdf, /osm/relation/{id}.rdf
A description of the feature — the real-world geographic object — including all OSM tags, provenance (PROV-O), and links to related resources. Returns RDF/XML by default; Accept: text/turtle returns Turtle. Uses OSM API 0.6.
/geo/osm/{type}/{id}.json, /geo/overpass/{type}/{id}.json
A description of the geometry — bare coordinate geometry for map rendering, with no semantic enrichment. Returns GeoJSON. Two upstream sources are available: the OSM API and the Overpass API (useful for complex multipolygon relations). Use the GeoJSON viewer to display results on a map.

What do the #id and #geo URI fragments mean?

Each OSM element is described by two related resources, distinguished by a hash fragment:

/osm/way/100#id
The feature — the real-world geographic object (a road, building, etc.) typed as spatial:Feature. Requesting /osm/way/100 (or /osm/way/100.rdf) returns an RDF document describing this resource. The hash fragment means the feature itself is never directly retrievable as a document; it is identified within the document at /osm/way/100, following the W3C hash-URI pattern for non-information resources.
/osm/way/100#geo
The geometry — a geom:Geometry resource carrying the spatial representation of the feature: a GML 3.2 literal (locn:geometry with datatype rdf:XMLLiteral: gml:Point, gml:LineString, gml:Polygon or gml:MultiSurface), centroid coordinates (geo:lat, geo:long), and links to the geometry endpoints. The feature links to its geometry via geom:geometry. The block has the same shape for nodes, ways and relations.

What URI patterns are supported?

Feature URIs

/osm/node/{id}, /osm/node/{id}.rdf, /osm/node/{id}.json
OSM node as RDF/XML or GeoJSON (XSLT-transformed from OSM API XML)
/osm/way/{id}, /osm/way/{id}.rdf, /osm/way/{id}.json
OSM way as RDF/XML or GeoJSON
/osm/relation/{id}, /osm/relation/{id}.rdf, /osm/relation/{id}.json
OSM relation as RDF/XML or GeoJSON
/changeset/{id}, /changeset/{id}.rdf
OSM changeset as RDF/XML

Geometry URIs (GeoJSON)

/geo/osm/{type}/{id}.json
GeoJSON geometry from OSM API
/geo/overpass/{type}/{id}.json
GeoJSON geometry from Overpass API (better for complex multipolygons)

Overpass feature URIs (RDF + GeoJSON)

/overpass/node/{id}, /overpass/way/{id}, /overpass/relation/{id}
Single feature fetched from Overpass API; same format options as OSM feature URIs

Bbox and search URIs

/nominatim/search?q={query}, /nominatim/search.json?q={query}
Nominatim place search; returns RDF/XML or GeoJSON
/overpass/features?bbox={W,S,E,N}, /overpass/features.json?bbox={W,S,E,N}
All features (nodes, ways, relations) in a bounding box from Overpass; returns RDF/XML or GeoJSON
/overpass/poi?bbox={W,S,E,N}, /overpass/poi.json?bbox={W,S,E,N}
Overpass points of interest in a bounding box; optional &filter= param (e.g. amenity=cafe or amenity)
/overpass/around?lon={lon}&lat={lat}&radius={m}
Overpass nodes within radius metres of a point; returns RDF/XML or GeoJSON
/tag/{key}
Tag information from taginfo.openstreetmap.org; returns RDF/XML or JSON-LD

How does content negotiation work?

All endpoints support two methods for selecting the response format:

File extension
Append .ttl, .rdf, .json, .gml or .html to element URIs (/osm/{type}/{id}); .json, .wkt or .kml to geometry URIs (/geo/osm/{type}/{id}).
HTTP Accept header
Accept: text/turtle (Turtle, the default), Accept: application/rdf+xml (RDF/XML, via Apache Jena), Accept: application/geo+json or Accept: application/json (GeoJSON), Accept: application/gml+xml (GML feature collection), Accept: text/html (HTML view).

A browser opening /osm/way/100 gets the HTML view: a map with the geometry and a table of the element's properties, plus links to every raw format. Only an Accept header that ranks text/html strictly above the data formats does that; a bare */* (curl and most clients) still gets Turtle, and an explicit extension always wins. The page itself loads /osm/{type}/{id}.json, so it shows exactly what the data formats carry.

How is the geometry built?

The same way for every element and every output format. The wrapper fetches the element from the OSM API (/node/{id}; /way/{id}/full and /relation/{id}/full, which include the member nodes and ways inline), parses the response once, and builds one geometry object in Java from it:

node
a Point.
way
a Polygon when the way is closed (first node equals last node, at least four nodes), otherwise a LineString.
relation with type=multipolygon or type=boundary
the member ways are stitched end-to-end into closed outer and inner rings, giving a Polygon or MultiPolygon. Only the requested relation's own members are used; member relations listed in the same response contribute nothing.
any other relation (routes, networks, ...)
a LineString over all member coordinates in member order, or no geometry at all when no member has coordinates.

That one object is then serialised into whichever format was asked for: the GML literal in the RDF #geo block, the osm:geometry element of the GML feature collection, the geometry member of the GeoJSON feature, and the GeoJSON, WKT and KML variants of /geo/osm/{type}/{id}. They always agree, because none of them is computed separately. Where no geometry could be built, the RDF has neither geom:geometry nor a #geo resource, GeoJSON has an empty GeometryCollection, and WKT is GEOMETRYCOLLECTION().

Inner rings of a MultiPolygon are attached to the first outer ring rather than to the one that contains them; nested multipolygons are therefore approximate.

Why does Overpass give better geometry for individual relations?

The Overpass query for a single relation uses >>, which recursively resolves all member relations, ways, and nodes in one round-trip. The OSM API /relation/{id}/full expands only one level deep: a relation whose shape is defined through member relations (a country made of subarea relations, a route made of route segments) has no member ways of its own in that response, so the OSM API path yields no or only a partial geometry for it, while Overpass returns the complete MultiPolygon.

How are large relations handled?

Way and relation responses in every format fetch /{type}/{id}/full from the OSM API, which returns every member way and every node of every way in one response. For large administrative or geographic boundaries this can be tens of megabytes of XML (the boundary of Germany, relation 51477, is about 34 MB). The wrapper does not hold this response as a string; it streams it once with a StAX parser, keeping only node coordinates, way node lists and the relation elements themselves, and builds the geometry from those. Member ways and nodes are therefore never fetched individually, and the parsed result is proportional to the number of distinct nodes rather than to the raw XML size.

The fetched response is cached for 24 hours and concurrent requests for the same relation share one upstream fetch, so a large relation costs the OSM API at most one /full request per day regardless of how often it is requested here. There is no member-count limit. Possible error codes:

509 Bandwidth Limit Exceeded / 529 Too Many Requests
The upstream OSM API rejected the request. The upstream error body is forwarded verbatim.
504 Gateway Timeout
The OSM API did not begin sending a response within the wrapper's 120-second client timeout.

For large relations the /geo/overpass/relation/{id}.json geometry endpoint is a better alternative, as it delegates geometry assembly to the Overpass API in a single query rather than fetching the full member graph from the OSM API.

Are responses cached?

The server caches the raw OSM XML it fetches from upstream (OSM API, Overpass API) for feature endpoints (/osm/node/*, /osm/way/*, /osm/relation/*). A single in-memory cache is shared across all response formats, so a request for /osm/relation/51477.json immediately followed by /osm/relation/51477.rdf results in only one upstream network request — the second request is served from the cached XML.

Capacity
Up to 2 GB of raw XML (entries are evicted by least-recently-used / low-frequency policy once the limit is approached).
Expiry
Entries expire 24 hours after they were written, consistent with the Cache-Control: public, Expires: +1 day headers sent to clients.
Concurrency
If the same URL is requested by multiple clients simultaneously, only one upstream fetch is performed; the other requests wait and share the result.
Scope
The cache is in-process and resets on webapp restart. Other endpoints (search, POI, around) are not cached server-side.

Why do I see 429 Too Many Requests errors?

To protect the upstream OSM, Nominatim, and Overpass services from excessive load, rate limiting is in place: each IP address may make 50 requests per 10 minutes. The allowance refills continuously, so after hitting the limit you regain roughly one request every 12 seconds. Requests over the limit receive HTTP status 429.

Registered heavy users can bypass the limit with an API key, sent as an HTTP header: 

Authorization: Bearer <your-api-key>

Contact the operator (see below) to request a key.
