What is the difference between feature data and geometry data?

There are two distinct kinds of endpoints:

/node/{id}.rdf, /way/{id}.rdf, /relation/{id}.rdf
Feature data — rich semantic descriptions including all OSM tags, provenance information (PROV-O), and links to related resources. Returns RDF/XML by default; requesting with Accept: text/turtle returns Turtle format. Uses OSM API 0.6.
/geo/osm/{type}/{id}.json, /geo/overpass/{type}/{id}.json
Geometry data — bare coordinate geometry for map rendering, with no semantic enrichment. Returns GeoJSON. Two upstream sources are available: the OSM API and the Overpass API (useful for complex multipolygon relations). Use the GeoJSON viewer to display results on a map.

Each OSM element also has a resource URI with a hash fragment (e.g. /node/1#id) that identifies the geographic feature itself (distinct from any document describing it), following W3C Linked Data best practices.

What URI patterns are supported?

Feature URIs (RDF + GeoJSON + GML)

/node/{id}, /node/{id}.rdf, /node/{id}.json, /node/{id}.gml
OSM node as RDF/XML, GeoJSON, or GML (XSLT-transformed from OSM API XML)
/way/{id}, /way/{id}.rdf, /way/{id}.json, /way/{id}.gml
OSM way as RDF/XML, GeoJSON, or GML
/relation/{id}, /relation/{id}.rdf, /relation/{id}.json, /relation/{id}.gml
OSM relation as RDF/XML, GeoJSON, or GML
/changeset/{id}, /changeset/{id}.rdf
OSM changeset as RDF/XML

Geometry URIs

/geo/osm/{type}/{id}.json
GeoJSON geometry from OSM API
/geo/osm/{type}/{id}.wkt
WKT geometry from OSM API
/geo/osm/{type}/{id}.kml
KML geometry from OSM API
/geo/overpass/{type}/{id}.json
GeoJSON geometry from Overpass API (better for complex multipolygons)

Derived data URIs

/search?q={query}, /search.json?q={query}
Nominatim place search; returns RDF/XML or GeoJSON
/map?bbox={W,S,E,N}, /map.json?bbox={W,S,E,N}
OSM API map data for a bounding box; returns RDF/XML or GeoJSON
/poi?bbox={W,S,E,N}, /poi.json?bbox={W,S,E,N}
Overpass points of interest (amenity nodes) in a bounding box
/around?lon={lon}&lat={lat}&radius={m}
Overpass nodes within radius metres of a point; returns RDF/XML or GeoJSON
/around.json?lon={lon}&lat={lat}&radius={m}
Overpass nodes within radius metres of a point; returns GeoJSON
/tag/{key}
Tag information from taginfo.openstreetmap.org; returns RDF/XML or JSON-LD

Why do some large relations return 509, 529, or 504?

All relation formats (RDF, GML, GeoJSON) fetch the /relation/{id}/full endpoint from the OSM API, which returns every member way and every node of every way in a single response. For large administrative or geographic boundaries this can amount to tens of megabytes of XML. There are three distinct failure modes:

509 Bandwidth Limit Exceeded / 529 Too Many Requests
The upstream OSM API (or Overpass API for /around queries) rejected the request because it would strain their capacity. The upstream error body is forwarded verbatim.
504 Gateway Timeout
The OSM API accepted the request but did not begin sending a response within the wrapper's 120-second client timeout. This is a client-side limit, distinct from an upstream rejection.

The following relations are known to be affected by size limits:

relation/71525.rdf | relation/71525.json | geo/osm/relation/71525.json
Paris administrative boundary — view on OSM
relation/13986332.rdf | relation/13986332.json | geo/osm/relation/13986332.json
Sebalder Reichswald forest — view on OSM

For large relations the /geo/overpass/relation/{id}.json geometry endpoint is a better alternative, as it delegates geometry assembly to the Overpass API in a single query rather than fetching the full member graph from the OSM API.

What do the #id and #geo URI fragments mean?

Each OSM element is described by two related resources, distinguished by a hash fragment:

/way/100#id
The feature — the real-world geographic object (a road, building, etc.) typed as spatial:Feature. Requesting /way/100 (or /way/100.rdf) returns an RDF document describing this resource. The hash fragment means the feature itself is never directly retrievable as a document; it is identified within the document at /way/100, following the W3C hash-URI pattern for non-information resources.
/way/100#geo
The geometry — a geom:Geometry resource carrying the spatial representation of the feature: WKT literal (locn:geometry with datatype geosparql:wktLiteral), centroid coordinates (geo:lat, geo:long), and links to the GeoJSON endpoints. The feature links to its geometry via geom:geometry.

Why do relations lack a WKT geometry in the RDF output?

For nodes and ways, the XSLT stylesheet can produce a WKT literal directly from the coordinates in the OSM XML response. For a type=multipolygon relation the geometry is more complex: the member ways are unordered fragments that must be stitched together into closed outer and inner rings before a MULTIPOLYGON(...) literal can be formed. This ring-assembly algorithm is not expressible in XSLT 2.0, so the #geo block in /relation/{id}.rdf carries only a centroid, not a WKT shape.

The GeoJSON geometry endpoints do not have this limitation — /geo/osm/relation/{id}.json and /geo/overpass/relation/{id}.json both run the ring-assembly in Java and return a correct MultiPolygon.

Thematic or organisational relations that group other features without defining a drawable shape (e.g. a route network or a list of countries) have no node coordinates at all; for these, neither geom:geometry nor a #geo resource is emitted.

Are responses cached?

The server caches the raw OSM XML it fetches from upstream (OSM API, Overpass API) for feature endpoints (/node/*, /way/*, /relation/*). A single in-memory cache is shared across all response formats, so a request for /relation/51477.json immediately followed by /relation/51477.rdf results in only one upstream network request — the second request is served from the cached XML.

Cache behaviour:

  • Capacity: up to 2 GB of raw XML (entries are evicted by least-recently-used / low-frequency policy once the limit is approached).
  • Expiry: entries expire 24 hours after they were written, consistent with the Cache-Control: public, Expires: +1 day headers sent to clients.
  • Concurrency: if the same URL is requested by multiple clients simultaneously, only one upstream fetch is performed; the other requests wait and share the result.
  • Scope: the cache is in-process and resets on webapp restart. Other endpoints (search, map, POI, around) are not cached server-side.

How does content negotiation work?

All endpoints support two methods for selecting the response format:

  • File extension: append .rdf, .json, or .gml to feature URIs; .json, .wkt, or .kml to geometry URIs.
  • HTTP Accept header: Accept: application/rdf+xml (RDF/XML), Accept: text/turtle (Turtle, via Apache Jena), Accept: application/geo+json or Accept: application/json (GeoJSON), Accept: application/gml+xml (GML, feature endpoints only).
