What is the difference between feature data and geometry data?

There are two distinct kinds of endpoints:

/osm/node/{id}.rdf, /osm/way/{id}.rdf, /osm/relation/{id}.rdf
Feature data — rich semantic descriptions including all OSM tags, provenance information (PROV-O), and links to related resources. Returns RDF/XML by default; requesting with Accept: text/turtle returns Turtle format. Uses OSM API 0.6.
/geo/osm/{type}/{id}.json, /geo/overpass/{type}/{id}.json
Geometry data — bare coordinate geometry for map rendering, with no semantic enrichment. Returns GeoJSON. Two upstream sources are available: the OSM API and the Overpass API (useful for complex multipolygon relations). Use the GeoJSON viewer to display results on a map.

What do the #id and #geo URI fragments mean?

Each OSM element is described by two related resources, distinguished by a hash fragment:

/osm/way/100#id
The feature — the real-world geographic object (a road, building, etc.) typed as spatial:Feature. Requesting /osm/way/100 (or /osm/way/100.rdf) returns an RDF document describing this resource. The hash fragment means the feature itself is never directly retrievable as a document; it is identified within the document at /osm/way/100, following the W3C hash-URI pattern for non-information resources.
/osm/way/100#geo
The geometry — a geom:Geometry resource carrying the spatial representation of the feature: WKT literal (locn:geometry with datatype geosparql:wktLiteral), centroid coordinates (geo:lat, geo:long), and links to the GeoJSON endpoints. The feature links to its geometry via geom:geometry.

What URI patterns are supported?

Feature URIs (RDF + GeoJSON)

/osm/node/{id}, /osm/node/{id}.rdf, /osm/node/{id}.json
OSM node as RDF/XML or GeoJSON (XSLT-transformed from OSM API XML)
/osm/way/{id}, /osm/way/{id}.rdf, /osm/way/{id}.json
OSM way as RDF/XML or GeoJSON
/osm/relation/{id}, /osm/relation/{id}.rdf, /osm/relation/{id}.json
OSM relation as RDF/XML or GeoJSON
/changeset/{id}, /changeset/{id}.rdf
OSM changeset as RDF/XML

Geometry URIs

/geo/osm/{type}/{id}.json
GeoJSON geometry from OSM API
/geo/overpass/{type}/{id}.json
GeoJSON geometry from Overpass API (better for complex multipolygons)

Overpass feature URIs (RDF + GeoJSON)

/overpass/node/{id}, /overpass/way/{id}, /overpass/relation/{id}
Single feature fetched from Overpass API; same format options as OSM feature URIs

Bbox and search URIs

/nominatim/search?q={query}, /nominatim/search.json?q={query}
Nominatim place search; returns RDF/XML or GeoJSON
/overpass/features?bbox={W,S,E,N}, /overpass/features.json?bbox={W,S,E,N}
All features (nodes, ways, relations) in a bounding box from Overpass; returns RDF/XML or GeoJSON
/overpass/poi?bbox={W,S,E,N}, /overpass/poi.json?bbox={W,S,E,N}
Overpass points of interest in a bounding box; optional &filter= param (e.g. amenity=cafe or amenity)
/overpass/around?lon={lon}&lat={lat}&radius={m}
Overpass nodes within radius metres of a point; returns RDF/XML or GeoJSON
/tag/{key}
Tag information from taginfo.openstreetmap.org; returns RDF/XML or JSON-LD

How does content negotiation work?

All endpoints support two methods for selecting the response format:

  • File extension: append .rdf, .json, or .ttl to feature URIs; .json to geometry URIs.
  • HTTP Accept header: Accept: application/rdf+xml (RDF/XML), Accept: text/turtle (Turtle, via Apache Jena), Accept: application/geo+json or Accept: application/json (GeoJSON).

Why do relations lack a WKT geometry in the RDF output?

For nodes and ways, the XSLT stylesheet can produce a WKT literal directly from the coordinates in the OSM XML response. For a type=multipolygon relation the geometry is more complex: the member ways are unordered fragments that must be stitched together into closed outer and inner rings before a MULTIPOLYGON(...) literal can be formed. This ring-assembly algorithm is not expressible in XSLT 2.0, so the #geo block in /osm/relation/{id}.rdf carries only a centroid, not a WKT shape.

The GeoJSON geometry endpoints do not have this limitation — /geo/osm/relation/{id}.json and /geo/overpass/relation/{id}.json both run the ring-assembly in Java and return a correct MultiPolygon.

Thematic or organisational relations that group other features without defining a drawable shape (e.g. a route network or a list of countries) have no node coordinates at all; for these, neither geom:geometry nor a #geo resource is emitted.

Why does Overpass give better geometry for individual relations?

The Overpass query for a single relation uses >>, which recursively resolves all member relations, ways, and nodes in one round-trip. The OSM API /relation/{id}/full expands only one level deep, and the GeoJSON conversion path does not reassemble member-way geometry the same way. For complex multipolygons in particular, Overpass reliably produces a correct MultiPolygon where the OSM API path may return only a centroid.

Why do some large relations return an error?

RDF and GML relation responses require fetching /relation/{id}/full from the OSM API, which returns every member way and every node of every way in one response. For large administrative or geographic boundaries this can be tens of megabytes of XML. The wrapper first fetches the lightweight /relation/{id} response to count way members; if the count exceeds 200 the request is rejected immediately rather than attempting a fetch that would time out or exhaust bandwidth. Possible error codes:

413 Content Too Large
The relation has more than 200 way members. The error message names the count and suggests the /geo/overpass/relation/{id}.json geometry endpoint as an alternative.
509 Bandwidth Limit Exceeded / 529 Too Many Requests
The upstream OSM API rejected the request. The upstream error body is forwarded verbatim.
504 Gateway Timeout
The OSM API did not begin sending a response within the wrapper's 120-second client timeout.

For large relations the /geo/overpass/relation/{id}.json geometry endpoint is a better alternative, as it delegates geometry assembly to the Overpass API in a single query rather than fetching the full member graph from the OSM API.

Are responses cached?

The server caches the raw OSM XML it fetches from upstream (OSM API, Overpass API) for feature endpoints (/osm/node/*, /osm/way/*, /osm/relation/*). A single in-memory cache is shared across all response formats, so a request for /osm/relation/51477.json immediately followed by /osm/relation/51477.rdf results in only one upstream network request — the second request is served from the cached XML.

Cache behaviour:

  • Capacity: up to 2 GB of raw XML (entries are evicted by least-recently-used / low-frequency policy once the limit is approached).
  • Expiry: entries expire 24 hours after they were written, consistent with the Cache-Control: public, Expires: +1 day headers sent to clients.
  • Concurrency: if the same URL is requested by multiple clients simultaneously, only one upstream fetch is performed; the other requests wait and share the result.
  • Scope: the cache is in-process and resets on webapp restart. Other endpoints (search, POI, around) are not cached server-side.
